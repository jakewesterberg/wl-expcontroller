# Spec map — how wl-expcontroller gets designed

- **Status:** proposed, for PI review
- **Date:** 2026-08-31
- **Companion:** `2026-08-31-controller-architecture-design.md` (the architecture these
  specs decompose)

The project is too large for one spec. This file names the pieces, what each owns, what
each is blocked on, and the order to take them. Each row becomes its own
brainstorm -> spec -> plan -> implementation cycle, the way `wl-works` and `wl-preproc`
were built.

**The schedule that governs everything:** the lab opens **January 2027**
(`wl-preproc/docs/CHECKPOINT.md`), wl-expcontroller is the day-one stack (D1), and v1
must reach the training ladder plus a first recording task (D2). Anything not on the
path to that is deferred by default, not debated.

## The specs

### S0 — Rig topology, hosts, and hardware
**Written: [`2026-08-31-S0-hosts-and-hardware-design.md`](2026-08-31-S0-hosts-and-hardware-design.md).**

**Owns.** Machine classes and roles (`rig/task`, `rig/eye`, `rig/sglx`, `rig/intan`,
`rig/sync`); task PC OS; DAQ verification; display panel and refresh target; procurement.

**Decided.** Ubuntu 24.04 LTS for the task PC with a Windows partition; the `rig/*` role
vocabulary; a 32-inch-class 16:9 flat OLED with the specific model deferred to a tandem
panel expected late 2026, plus a bench panel bought now so M1/M2 are not blocked on a
launch; the display geometry as a formula with ~50 cm as the build target; and the DAQmx
bench-verification procedure.

**Blocked on.** Nothing. **Blocks.** Purchasing, and therefore everything.

**Urgent.** NI cards are 12–13 weeks out and the board spec says order now. The
`PCIe-6343` on Linux is **UNVERIFIED** and becomes the first bench test when a card lands
(P10). This spec should be short and fast.

---

### S1 — Task model and authoring API
**Owns.** The within-trial declarative vocabulary; the between-trial Python surface; the
Python declaration representation; validation; the rendered-diagram review artifact;
the escape-hatch policy.

**Decides.** Open question #1 — strictness — **by writing two real tasks both ways**
(a fixation/detection task and one with adaptive difficulty) and comparing what review
and verification actually feel like. Not settled from first principles.

**Blocked on.** S2 (codes are declared in tasks). **Blocks.** S4, S5, S6, S8, S9, S10.

**Note.** This is the pivot. It is also the spec where D4 (model-authored tasks) is
either honored or quietly abandoned; the acceptance test is whether a generated task can
be reviewed from a diagram and 5,000 simulated trials without reading source.

---

### S2 — Event vocabulary and hardware truth
**Owns.** The numeric event-code allocation, jointly with `wl-mllib` (which publishes it)
and `wl-preproc` (which decodes it); word semantics; strobe timing; the rule that codes
are allocated, never invented.

**Blocked on.** Agreement with `wl-mllib`. **Blocks.** S1, S10, and every recording.

**Note.** Nothing is allocated anywhere today. This is a v1 blocker with a cross-repo
dependency, so it starts early even though it looks like bookkeeping.

---

### S3 — Sync and timing integration
**Owns.** The division of labor with `wl-sync`: who mints session identity, where the
barcode lands, how our events reach the recorders, photodiode patch roles and placement,
camera sync, and the offline reconstruction round-trip.

**Blocked on.** Nothing. **Blocks.** S6, S10.

**Note.** Mostly *reconciliation*, not invention — `wl-sync` already owns most of it.
The real work is deleting our duplicate concepts and agreeing patch placement against
the real optics (open question #4).

---

### S4 — Stimulus presentation
**Owns.** `DisplayAdapter`; the stereo viewport model and cyclopean coordinates; per-eye
geometry and calibration; static and moving stimuli with deterministic reconstruction;
natural-image asset handling; the audio subsystem and its verification tap; test screens
including the per-eye alignment target.

**Blocked on.** S0 (panel), S1 (vocabulary). **Blocks.** S9, and the V1/V7/V9 protocols.

**Note.** Stereo is built as viewports from day one even though v1 is monocular — that is
what makes the monocular task the zero-disparity case rather than a separate path.

---

### S5 — Eye tracking, calibration, and gaze
**Owns.** OpenIrisDPI UDP ingest and staleness accounting; the OpenIris remote API for
session-aligned eye recording; online saccade detection as a versioned component; the
versioned gaze mapping with its change log; recentering, drift correction, calibration
interludes.

**Blocked on.** S1, S4 (calibration draws to the display). **Blocks.** S9, V3.

**Note.** Carries the project's dominant scientific risk: the ~2% of tracker frames
>= 10 ms. V3 runs early, on our own hardware, before window parameters are frozen.

---

### S6 — I/O subsystem
**Owns.** NI DIO out (event words, reward commanded, stim trigger) and in (both
photodiode comparators, chair motion, RHS stim output); analog in (eye copy, joystick,
misc); reward command path to `wl-juicer`; camera triggers; the `wl-shook` motion gate.

**Blocked on.** S0 (card verified), S2 (word format), S3. **Blocks.** S7, S8, V2/V2b.

---

### S7 — Neural plane and stimulation
**Owns.** `neurofeatd` (SpikeGLX) and `rhxfeatd` (Intan); the shared `FeatureSource`
interface and message schema; the RHX backpressure mitigation (P14); stim parameter push,
read-back and bounds; delivery counting against the RHS stim-output line; blanking
windows; tier-3 gating and the runaway detector.

**Blocked on.** S6, S8 (welfare bounds). **Blocks.** V4, V8.

**Split.** Stim **tiers 1 and 2 are v1 and live in S6/S8**, not here. S7 is tier 3 —
post-v1 — plus the feature interface both tiers eventually share.

---

### S8 — Session and experiment management
**Owns.** The block/interlude structure; the trial scheduler (condition selection,
re-queue policy, counters); the parameter model, staging, atomic ITI application and
per-trial snapshots; the bounded config and its precedence chain; fluid, session and
token accounting; the validated write path and its arbitration rule; restart safety.

**Blocked on.** S1. **Blocks.** S9, S10.

**Welfare-critical.** Most of this file requires human review before merge (CLAUDE.md).
Keep the welfare modules small and separately listed.

---

### S9 — Operations and console
**Owns.** The console process and its ZMQ link; preflight; one-action launch; pause and
emergency stop; manual reward; the generated parameter panel; per-condition counters;
abort-reason readout; live plots and the plot vocabulary; keyboard/mouse demo mode;
simulated sessions and behavior agents; test screens; remote console; the toolkit choice.

**Blocked on.** S1, S8. **Blocks.** the D4 acceptance test.

**Note.** Demo mode, simulated sessions and hardware dropped-frame monitoring are **not
nice-to-haves** — they are the verification loop that makes model-authored tasks safe.
They carry v1 status.

---

### S10 — Data outputs and lab integration
**Owns.** The session directory layout; JSONL and parquet outputs; the config and
provenance snapshot; DONE markers against `wl-preproc`'s published schema; the `labhost`
endpoint implementing `wl-preproc`'s lab-host protocol (live state as readings, a small
non-welfare action vocabulary); and the session-summary file the ingest path carries.

**Blocked on.** S2, S3, S8. **Blocks.** ELN autopopulation.

**Cross-repo.** The wl-works amendment is drafted at
`docs/pending-wl-works-amendments.md`, not assumed; another worker owns that repository. It
builds on `wl-preproc`'s lab-host protocol, which is itself proposed rather than agreed, so
both move together if that one is reshaped.

---

### S11 — Packaging, deployment, and CI
**Owns.** `wl.yaml` and the `wl-orchestrator` registry entry (**the registry does not know
this project exists today**); the `wl-stack` rig playbook; the simulator/CI harness;
version pinning; the license decision (ADR-0004).

**Blocked on.** S0. **Blocks.** rig rollout.

---

### S12 — Parity check and swap verification
**Owns.** The MonkeyLogic feature list used as a *completeness check* over §15's derived
inventory; and the one-time verification that a MonkeyLogic rig can be stood up on the
same hardware and produce the same recorded streams (D3).

**Blocked on.** v1 existing. **Blocks.** nothing.

**Note.** Deliberately last and deliberately small. Under D3 the swap is a rig-contract
property, not a maintained task library, so this is a verification exercise rather than
a parallel development effort. Running it earlier would invert P2.

---

## Deferred by default

Not scoped, not promised, revisited only if v1 lands early or a concrete second consumer
appears: home-cage or freely-moving paradigms, a general community framework, a GUI task
builder, hard real-time guarantees, and any abstraction whose only consumer is imagined.

---

## Validation runs alongside, not after

`docs/validation.md` gains V2b (digital-input read latency), V7 (audio onset timing),
V8 (RHX backpressure headroom) and V9 (display geometry and per-half photometry), and
widens V4 to cover both neural paths. Every spec above names the protocols it must satisfy, and
a protocol without a committed artifact under `docs/measurements/` does not count
(pitfalls P1).
